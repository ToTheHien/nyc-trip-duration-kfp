## The run sequence

Five runs produce every proof this plan owes. Run them in this order, recording each run id as you go. All of them use the same component image tag, which is REQ-B8's one real precondition.

| Run | Parameters | Purpose |
|---|---|---|
| A | `--start-month 2020-02 --end-month 2020-04 --features-version v1` against an empty registry | REQ-B4 full DAG reaching `register`; REQ-B7 promoting direction; REQ-B9 success-path exit task |
| B | identical to A | REQ-B10 caching-enabled baseline: tasks reused from cache |
| C | as A but `--features-version v2` | REQ-B10 the one documented input change and its invalidation cascade; REQ-B7 non-promoting direction via the exact-tie rule; REQ-B4 documented skip branch |
| D | identical to A plus `--no-cache` | REQ-B8: forces genuine re-execution so the same deterministic keys are rewritten and can be diffed |
| E | `--start-month 2018-01 --end-month 2018-01` | REQ-B9 failure path: the raw object does not exist in `tlc-raw`, so `ingest` fails loudly and the exit task must still fire |

Run C's non-promoting direction is produced without any tuning surface and without any fabricated model: identical input data and a deterministic LightGBM configuration (`random_state=42`, `n_jobs=1`, `deterministic=True`) yield an identical model and therefore an RMSE exactly equal to the incumbent's, and `lib.evaluate.beats_champion` resolves an exact tie in the incumbent's favour. If, contrary to expectation, run C's RMSE differs from run A's, do not manufacture a worse model — instead seed the incumbent by setting the champion version's RMSE tag to a deliberately low value through the same alias-and-tag API `lib/registry.py` exposes, re-run, and **disclose that seeding explicitly in README's evidence section** as a deliberately set precondition. Either path is honest; an undisclosed one is not.

Two small ranges also need exercising while the cluster is up, because they are cheap and they close edge cases no compile-time test can reach: a single-month range that still straddles nothing but ingest (use run E's shape with a month that does exist, and let it fail at `train` with the empty-side ValueError, recording that as the documented behaviour), and an overlapping-range pair sharing one month, to show that the shared month's deterministic key is overwritten with identical bytes rather than appended to.

Re-submitting identical parameters with caching enabled reuses every task and rewrites nothing, so the two checksums would be trivially equal because only one execution ever happened — which is exactly the hollow proof PITFALLS.md Pitfall 5 warns about. Disabling per-run caching forces genuine re-execution of the whole DAG, so the same deterministic keys are recomputed from the raw data and overwritten, and the comparison is between two independent executions.
