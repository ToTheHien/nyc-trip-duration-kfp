Produce the two external-data artifacts the rest of Phase 2 consumes: the gitignored 12-month TLC Parquet cache (D-07, REQ-D1) and the committed 263-row zone-centroid lookup table (D-06) that makes a haversine distance computable at all in a dataset that carries no coordinates.

Without a static zone-to-coordinate table there is no distance feature and REQ-C2 has nothing to vectorize. The real 12-month download is what makes the REQ-C5 benchmark and the REQ-C4 chunked-read proof credible rather than a toy claim.

Write `scripts/precompute_zone_centroids.py`, a one-time maintainer script that turns TLC's public taxi-zone shapefile into the committed `data/zone_centroids.csv` that the D-06 haversine join reads.

Flags: `--url` defaulting to `https://d37ci6vzurychx.cloudfront.net/misc/taxi_zones.zip`, `--out` defaulting to `data/zone_centroids.csv`, `--work-dir` defaulting to a temporary directory cleaned up afterwards.

Pipeline, in order:

1. Download the archive over HTTPS from the CloudFront host. The legacy direct-S3 host answers 403 and must not be used.
2. Extract with `zipfile`, validating every member before writing: resolve the join of the destination directory and the member name, and refuse any member that is absolute, is a symlink, or whose resolved path escapes the destination directory. A trusted-looking source does not make unvalidated archive extraction acceptable; this is the T-02-03 mitigation and it costs a few lines.
3. Read `taxi_zones.shp` with `pyshp`'s `shapefile.Reader`. Take the zone identifier from the dbf record's `LocationID` field, resolved by field name, not from the record's positional index.
4. For each shape, compute an area-weighted centroid from the raw vertex rings using the shoelace formula shown in RESEARCH.md Pattern 2: compute each ring's own signed-area-weighted centroid, then combine rings weighted by absolute area. Split rings on the shape's `parts` index boundaries. 23 of the 263 zones are multi-part, and averaging vertices across their disjoint parts — or taking a bounding-box midpoint — puts the point outside the zone entirely. Handle a degenerate zero-area ring by falling back to the arithmetic mean of its vertices, exactly as the verified helper does.
5. Reproject each resulting point from EPSG:2263 to EPSG:4326 with `pyproj.Transformer.from_crs("EPSG:2263", "EPSG:4326", always_xy=True)`, constructing the transformer once at module scope rather than per zone. The shapefile's own `.prj` declares NAD83 State Plane New York Long Island in US survey feet — RESEARCH.md read it directly. Omitting this step yields values in the hundreds of thousands that look like data but are not degrees.
6. Before writing anything, assert the shape count is exactly 263 and fail loudly with the observed count otherwise. Also assert every emitted latitude lies within [40.4, 41.1] and every longitude within [-74.30, -73.65], and that zone 1's centroid sits within 0.01 degrees of latitude 40.6918 and longitude -74.174. RESEARCH.md validated this exact computation against Newark Liberty Airport's real coordinates, making it a cheap end-to-end correctness proof of the whole read-compute-reproject chain.
7. Write the CSV sorted ascending by `zone_id`, with header `zone_id,centroid_lat,centroid_lon`, formatting coordinates to 6 decimal places — roughly 0.1m resolution, far finer than a zone centroid means anything at, and it keeps the committed file byte-stable across runs.

Emit no rows for LocationID 264 or 265. TLC's lookup table lists 265 IDs, but 264 (`Unknown`) and 265 (`Outside of NYC`) are placeholders with no polygon, so no centroid exists for them. Plan 02-04 handles trips that reference them.

Run the script, commit the resulting `data/zone_centroids.csv`, and confirm git tracks it rather than ignoring it.
  </action>
